## Findings and status

- **CIDR matching — fixed.** The earlier `/9` matcher effectively rounded the prefix to whole octets and could accept an address outside the requested network. A synthetic `10.128.0.0/9` negative case previously drew a likely-failure judgment (0.73); on the corrected code, the corresponding incorrect-acceptance judgment was 0.06, while a valid `/8` positive control was 0.90. Current code validates IPv4 octets/prefix and applies the prefix bitmask. `test_viz_ui.js` contains UI filter controls. This is supported by deterministic code behavior and regression coverage, not Jev alone.
- **Uninstaller name collision — fixed.** The earlier behavior could remove same-named foreign tasks, firewall rules, or shortcuts without verifying ownership. Current code checks task action, description and product script marker; shortcut target/arguments/description and launcher marker; and the firewall rule's UDP/514, inbound allow, LAN scope and profiles. Preflight fails closed before mutation when ownership is unknown. The updated tests cover foreign same-name task/firewall resources and owned legacy watchdog compatibility.
- **Purge/UAC behavior — explicitly bounded.** `-PurgeLogs` runs unelevated before UAC and is not forwarded to the elevated child; requesting it from an already elevated shell refuses. Default uninstall preserves logs. Tests cover preflight/purge failure, UAC cancellation after purge, and elevated-child failure messaging. If UAC is cancelled after the purge, logs are already gone while Windows resources remain; the warning/error states this.
- **Residual purge race — unresolved limitation.** The purge code checks the target and descendants for reparse points before recursive deletion. A same-user process could replace a checked path with a reparse point between the final check and name-based `Remove-Item -Recurse`. Jev previously assigned 0.87 to this residual race. The test proves rejection of a static nested junction, not protection against concurrent path replacement. Do not treat purge as race-free against another process running as the same user.
- **Event recovery boundary — documented behavior, not an undisclosed guarantee.** During SQLite unavailability, the receiver stages recoverable batches in a 64 MiB journal. If the journal also cannot accept a batch, raw logging continues while searchable event-index history can have a gap; status exposes missed rows/recovery state. README documents this boundary. An earlier broad question about the recovery gap scored 0.49 (inconclusive); source, status code, and docs were reviewed directly.
- **Timeline and compatibility limits.** Lifetime message aggregates are placed once at their row's last-observed UTC date; sampled values are examples and do not reconstruct historical per-event distributions. The compact chart feed falls back to the legacy full-data chart when its row/size limits are exceeded or the requested settings cannot be represented compactly. These paths are described in code/docs; they remain capacity/precision limits, not proof of a correctness defect.
